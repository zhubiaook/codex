# Use typed Responses Provider configuration in the Go SDK

The Go SDK will configure at most one Responses-compatible Provider per Client through a typed, optional Provider value; absence selects the Built-in OpenAI Provider. A Responses-compatible Provider requires an absolute HTTP(S) base URL, a Provider Default Model, and an explicit closed authentication value representing either a bearer token supplied directly by the caller or no authentication. Its human-readable name is optional, its internal provider ID is hidden, HTTP/SSE is the default transport, and WebSocket support is an optional capability. Threads may override the Provider Default Model.

The SDK will remove the public structured configuration map and the misleading top-level base URL rather than preserve two configuration models. Unmodeled CLI configuration remains available only through a nested experimental raw-override facility, which may not override fields managed by the typed Provider. Existing top-level API-key behavior remains available only for the Built-in OpenAI Provider, and conflicts with an explicitly configured Responses-compatible Provider are rejected.

Provider structural errors are returned by Client construction as typed validation errors with stable field paths. Base URLs are rejected if they are relative, use a scheme other than HTTP(S), contain user information, a query, or a fragment, or end in the final `/responses` route; configuration strings with surrounding whitespace are rejected rather than rewritten. Thread construction will also return an error so invalid Thread options fail before the first Turn. These breaking API replacements will be made before the Go SDK's first stable release instead of carrying a second deprecated configuration path.
